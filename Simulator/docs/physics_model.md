# RumiCar Simulator — 車両物理モデル解説(詳細版)

> アプリ内「🔬 物理モデル」ダイアログの長文版です。各定数の実数値・導出・設計意図を、後から読み返し/自分で調べた内容との対比に使えるようまとめています。
> 実装本体: `public/js/physics_dyn.js`(動力学エンジン), `public/js/physics.js`(クラシック=キネマティック版), `public/js/physics_v2.js`＋`public/js/contact_v2.js`(精密 v2 エンジン=4輪 two-track＋インパルス接触・§13), `public/js/config.js`(`REGIMES` / `DYN_DRIVE` / 車種パラメータ)。

## 0. 全体像 — 何を解いているか

画面の車は、**タイヤが路面に生む力**を毎フレーム積分して動く**シングルトラック(自転車)モデル**です。アンダーステア・オーバーステア・ドリフト・スピン・ホイールスピン・ロックは、どれも個別ルールの「演出」ではなく、**この一つの力学から創発する結果**です。

3つの物理エンジンを切替できます(ツールバー下「物理エンジン」セレクト・v3.52.0 から):

| | 動力学モデル(既定) | クラシック物理 | 精密 v2 (§13) |
|---|---|---|---|
| 実装 | `physics_dyn.js` | `physics.js` | `physics_v2.js`＋`contact_v2.js` |
| 原理 | タイヤ力を積分(u, v_lat, r を独立に)・シングルトラック | 速度=幾何で決まる(運動学) | **4輪 two-track**(輪別荷重・デフ・車輪 ODE)＋**インパルス接触** |
| 横滑り | 力から創発(90°超の過渡も可) | 速度ベクトルが車体 ±45° に拘束=構造的に出ない | 力から創発(結合スリップ MF・輪別) |
| 用途 | 既定。ドリフト/バックエントリー/ドーナツ | 滑らかで予測しやすい。初学者向け | フルスケール競技(推奨)・卓上スリップタイヤ学習 |

本解説の §1〜§8 は**動力学モデル(既定)**の解説です。精密 v2 エンジンが何をどう変えるかは **§13** にまとめています(卓上の既定は動力学モデルのまま=従来挙動・記録と byte 単位で不変)。

実行レート: ユーザープログラム `loop()` = 20Hz、物理積分 = 60Hz。

## 1. 運動方程式(シングルトラックモデル)

前後輪を左右まとめて1本ずつに集約し、重心 (CG) 基準で3つの状態量を時間積分します。

- `u` : 車体前後速度 (m/s, 前+)
- `v_lat` : 車体横速度 (m/s, 左+)
- `r` : ヨーレート (rad/s, 反時計+)

質量 `m`、ヨー慣性 `I_z`、前軸距離 `a`、後軸距離 `b`(`a + b = L` = ホイールベース):

```
m·(u̇   − v_lat·r) = Fx_前 + Fx_後        … 前後方向(遠心項 −v_lat·r 込み)
m·(v̇_lat + u·r)   = Fy_前 + Fy_後        … 横方向(遠心項 +u·r 込み)
I_z·ṙ             = a·Fy_前 − b·Fy_後     … 回頭モーメント
```

第3式が回頭の綱引きです。`a·Fy_前 − b·Fy_後 > 0` が残ると車は回り続けます(ドリフトの自走)。ドリフト車で後輪横μを下げる(`muRK<1`)のは、後輪を先に飽和させてこの項を残し、回頭を自走させるためです。前後同時飽和だとモーメントが釣り合い、中立の4輪ドリフトで止まってしまいます(実測)。

公開座標 `x, y` は互換のため後輪軸中心(CG から `b` 後方)、内部 `_cx, _cy` が CG。

## 2. 摩擦円(摩擦楕円)— タイヤ力の上限

各タイヤの前後力 `Fx` と横力 `Fy` は、合計が円(楕円)の内側に制限されます。

```
(Fx / (μx·n))² + (Fy / (μy·n))² ≤ 1     (n = そのタイヤの荷重)
```

- 縦に使い切る → 横が残らず膨らむ(アンダー、ホイールスピン)
- 横に使い切ったところへ駆動を足す → 滑り出す(オーバー、スピン)

### 異方性 vs 等方性(領域で変わる)

| 領域 | μy(横) | μx(縦) | 円の形 | 理由 |
|---|---|---|---|---|
| 卓上 | 0.19 (drift 0.13) | 0.75 (drift 0.35) | 縦長の楕円 | **意図的な工夫**(下記) |
| フルスケール | 1.4 (drift 1.0) | 1.4 (drift 1.0) | 等方の真円 | 本物のタイヤ |

> **現実との違い:** 卓上スケール(ホイールベース 0.13m・最高速 0.7m/s)では、実際の μ≈1(横限界 ≈ μg = 9.8 m/s²)に対し全開全舵でも到達できる横加速度が小さく、**絶対に滑りません**。そこで卓上は横 μ を小さく(楕円を縦長に)して「滑り出しが目で見える」ようにしています。到達可能な最大 a_y は全舵全速で ≈1.74 m/s² なので、ノーマル(横限界 1.86)はギリ滑らず、ドリフト(横限界 1.28)は全舵 u≈0.61 で滑り出します(旧モデルの「PWM215 で滑り出し」と一致するよう較正)。

摩擦円の結合度は領域パラメータ `circleBi`(`physics_dyn.js` の `DYN.circleBi`):

- `circleBi = 0`(卓上)= 片方向(縦優先)。駆動輪が空転すると横力がほぼゼロに落ちる(=パワーオーバー/ドーナツの母体)。卓上のスリップタイヤは wheelspin 律速なのでこれが物理的に正しい。
- `circleBi = 1`(フルスケール)= 等方ラジアル円。combined-slip でグリップ限界、横荷重が縦力を削る。

## 3. 横力 — スリップ角とタイヤ曲線(簡易 Pacejka, F4)

タイヤは「向いている方向」と「進む方向」のズレ(スリップ角 `α`)に応じて横力を生みます。

```
線形域(小α):  Fy ≈ C·α              C = コーナリング剛性(踏ん張りの強さ)
ピーク超え:     Fy = Fy_max / (1 + k_decay·(|α| − α_peak))   (|α| > α_peak)
```

- `|α| ≤ α_peak`: 横力は摩擦楕円のピーク `Fy_max` フル。
- `|α| > α_peak`: 緩やかに減衰(ゼロには落とさない)。
- スリップ角は物理域 `(−π/2, π/2)` に束縛(`tan` のラップによる符号反転を防止)。

| 領域 | α_peak | k_decay | 意味 |
|---|---|---|---|
| 卓上 | 1.35 rad | 0.50 | 粘る。落ち込み過大は全速ドリフトを殺す既往退行があるため浅め |
| フルスケール | 0.25 rad (≈14°) | 0.60 | 実タイヤ同様に早期ピーク・限界後はやや深く落ちる |

コーナリング剛性の基準 `C0`: 卓上 10.0、フルスケール 60.0(m/s²/rad, 質量正規化)。無次元化 `Cα* = C0/(μ·g)` で領域を横断して比較できます。

### アンダー/オーバーステアの正体

前後のコーナリング剛性の**比**が定常ゲインの速度依存(=US/OS 勾配)を決めます。`DYN_DRIVE` の `CfK`(前)/`CrK`(後)倍率:

| 駆動 | CfK | CrK | 傾向 |
|---|---|---|---|
| FF | 0.95 | 1.30 | 前が弱い → アンダー |
| FR | 1.15 | 1.00 | 前が強い → オーバー寄り |
| 4WD | 1.00 | 1.10 | 中立寄り |

## 4. 前後力 — 駆動・制動・荷重移動

### 駆動配分 `split`(`DYN_DRIVE`)

| 駆動 | split [前, 後] | 重心 a/L (`aFrac`) |
|---|---|---|
| FF | [1.0, 0.0] | 0.42(前寄り) |
| FR | [0.0, 1.0] | 0.55(後寄り) |
| 4WD | [0.4, 0.6] | 0.50(中央) |

> **RumiCar 実機の特性そのまま:** BRAKE は摩擦ブレーキではなく**モーターブレーキ**で、駆動輪にしか効きません(制動も `split` で配分)。したがって FR はリアのみ制動=ロック気味で回頭(ブレーキドリフト)、FF は前のみ=直進安定、が構造から出ます。後輪横μ倍率 `muRK`(FR 0.80 / 4WD 0.95 / FF 1.05)も合わさり、FR のブレーキオーバーが顕著になります。

### 荷重移動(前後・左右)

**前後荷重移動(全領域共通・Phase B):**

```
Δn = m·a_x·(h/L)      h/L = hOverL = 0.35(重心高/ホイールベース)
```

加速で後軸へ、制動で前軸へ荷重が移動。軸荷重 `n`(=`nF`/`nR`)が動くと摩擦円半径 `μ·n` が前後で変わり、「制動中はリアが軽い=滑りやすい」が出ます。卓上ベンチに較正済みのため領域フェードはせず**全領域共通**です。

**左右(横)荷重移動(フルスケールのみ・IMP-01 / Z2):**

シングルトラック(自転車)モデルは左右輪を持たないため、旋回での外内輪荷重移動は**タイヤ荷重感度**(load sensitivity:接地荷重が増えるほど μ が目減りする非線形性)として軸単位に畳み込んで導入します。前ステップの横タイヤ力 `ayLat`(質量正規化・代数ループ回避のため1ステップ遅延)が重心高×トレッドで外内輪へ荷重を移し、外内2輪の感度を解析的に畳んだ**軸グリップ係数**

```
gmF = max(0.5, 1 − latLoadK·(φF·ayLat/nF)²)
gmR = max(0.5, 1 − latLoadK·((1−φF)·ayLat/nR)²)      φF = b/L(前軸静的荷重比)
```

を各軸の横容量 `FyF`/`FyR` に掛けます(導出:`μ(Fz)=μ0·(1−k·ΔFz/w)` の外内輪和 = `μ0·N·(1−k·(ΔFz/w)²)`)。下限 0.5 のクランプは、極端な荷重移動でグリップが全壊して即スピンするのを防ぎます。

- **領域フェード(`latLoadK`):** フルスケール=`0.05` / 卓上・中スケール=`0`(寄与ゼロ=恒等)。`latLoadK = 0` のときこのブロックは丸ごとスキップされるため、卓上は摩擦円の双方向結合(`circleBi`)と同型に従来経路と**バイト単位で完全一致**します(byte 不変)。
- **US/OS の創発:** φF は静的荷重比なので**定常旋回では前後が均等に目減り**し、Froude 相似のフルスケールゲート(Ay*・§7)を壊しません。ところが前後荷重移動(`hOverL`)で `nF`/`nR` が静的比からずれると `gmF`/`gmR` の相対目減りが非対称になり、**荷重連成の US/OS が創発**します(トレイル制動 → `nR`↓ → `(φ·ayLat/nR)²`↑ → `gmR`↓ = リア抜け=オーバーステア)。効果は**トレイル制動・複合荷重(加速旋回/制動旋回)に自己集中**します。
- **係数根拠:** `latLoadK = 4·loadSens·(h/track)²`。重心高 `h ≈ 0.45 m`・トレッド `track ≈ 1.6 m` → `(h/track)² ≈ 0.079`、荷重感度 `loadSens ≈ 0.158`(荷重倍化で横グリップ約16%減=乾燥レースタイヤ相当)→ `latLoadK ≈ 0.05`。sweep 実測で Part F ゲート(`Ay* > 1.05`)は 0.06 まで維持・0.08 で割れるため、余裕を残して **0.05** を採択しています。
- 学習側には荷重・接地荷重 `Fz` を一切晒しません(前方 ToF×3 のみ・方針 D-1)。

## 5. 車輪スリップ率/縦力(フルスケールのみ, F5)

フルスケールでは車輪の回転を状態化します(`wheelDyn = 1`)。車輪面速度 `vw = ω·R` を陽的 Euler 積分し、スリップ率から縦版 Pacejka で縦力を出します。

```
s  = (vw − u) / |u|                       スリップ率
Fx = μx·n·sin(wheelC·atan(wheelB·s)) / 正規化(sPeak)   縦版 Magic Formula
```

フルスケール値: `sPeak = 0.10`(乾燥アスファルト)、`wheelB = 14.0`、`wheelC = 1.7`、`wheelLambda = λ = m·R²/Iw = 28.0`(車輪応答の速さ)。定出力ドライブトレイン `wheelPower = 547`、`launchAccel = 15.0`:低速はトルク律速 `launchAccel·accel`、高速は出力律速 `wheelPower/|u|`。

創発する挙動: 発進で**ホイールスピン**(トルク>グリップで空転損失 → スルーレート制御に負ける)、急制動で **ロック**(`s → −1` で横グリップ喪失)。251km/h で hook-up し、定常巡航 347km/h は `s≈0.01 < sPeak` で空転せず抗力律速。

> 数値安定: 車輪時定数 `1/(λ·∂Fx/∂vw)` が積分刻み `h` より速いと陽的 Euler が発散するため、`λ·(∂Fx/∂vw)·h < subSafety` を満たすよう適応サブステップ `nSub` を増やします(`adaptiveSub`)。

「車輪エンコーダ(任意)」を有効化すると `RC_wheel_speed(FRONT/REAR)` で前後の車輪面速度が読め、前後差からスリップ率を推定してトラクション制御や ABS を自作できます。

## 6. 空力 — 抗力とダウンフォース(フルスケールのみ, F3)

速度の2乗に比例する2つの力(`½·ρ·係数·A·u²`):

```
抗力        Fd = ½·ρ·Cd·A·u²    常に減速側(縦に逆向き)
ダウンフォース Fl = ½·ρ·Cl·A·u²    荷重 n を増やす(前後 downforceBalance で配分)
```

フルスケール値: `ρ = 1.225`、`Cd = 0.9`、`Cl = 3.0`、`frontalArea A = 1.3 m²`、`downforceBalance = 0.45`(前軸寄り)。

- **「速いほど曲がれる」:** ダウンフォースが荷重 `n` を `u²` で増やし、摩擦円半径 `μ·n` が速度依存になる。卓上では `ρ = 0 / A = 0` で完全に no-op(動圧ゼロ)。卓上スケールでは v² が小さく空力はフルスケール比で約7万分の1=実質無視できるため。
- **最高速は自然決定:** 駆動力 = 抗力 で釣り合った速度が頭打ち(設定 `maxSpeed = 110` は目標値で、実際の頭打ち ≈347km/h は釣り合いの結果)。

## 7. 領域(スケール)と動的相似(F1)

同じ動力学エンジンを3スケールで動かします。挙動の鍵は支配比:

```
Ay* = (v²/R) / (μ·g)     必要な横加速度 ÷ 路面が出せる横加速度。1 を超えると滑る
```

| 領域 | L (ホイールベース) | 最高速 | 速度表示 | ToF レンジ | 摩擦 | 空力 | 車輪スリップ |
|---|---|---|---|---|---|---|---|
| 卓上 | 0.13 m | 0.7 m/s (≈1.3km/h) | 相対補正 (≒350/180) | 2,000 mm | 異方 | なし | なし |
| 中スケール | 0.26 m | √2 倍 | 相対補正 | 4,000 mm | 異方 | なし | なし |
| フルスケール | 2.6 m | ≈347 km/h | 実速度 ×3.6 | 150 m | 等方実μ | あり | あり |

### 卓上 ↔ 中スケール = Froude 相似(相似保持)

長さを `kL` 倍するとき、速度を `kV = √(kL·kG·kμ)` 倍・時間を `kT = √(kL/(kG·kμ))` 倍・加速度を `kG·kμ` 倍にスケールすると **Ay* が不変**になります。結果:**同じ走行プログラムが、大きく速い世界でも同じ操作で同じように滑り出す**。中スケールは `kL=2`(`scaleRegime` で生成)。

```
kV = √(kL·kG·kμ)   速度    (maxSpeed, uBlend, absUFloor, uStop …)
kA = kG·kμ          加速度  (accel, brake, coast, C0)
kT = √(kL/(kG·kμ))  時間    (steerRate, vlatStop は ÷kT)
```

無次元の形状係数(タイヤ曲線の `α_peak`/`k_decay`)は Froude 相似で不変なので卓上値を引き継ぎます。

### フルスケール = 相似破れ(意図的)

卓上の異方性ハック(μy≪μx)をやめて**等方の実 μ**にし、**空力**・**左右荷重移動**(`latLoadK`・§4)・**車輪スリップ**を有効化します。`kinFade` も 0 にして入力側の操縦シム(`kinFactor`/`steerK`)を撤去し、US/OS を純粋に物理から創発させます。これらの切替は全て**連続ブレンド**(二値切替禁止)で、領域間に不連続帯を作りません(`circleBi 0→1`・`kinFade 1→0` が相似破れと同じ境界)。

## 8. 操縦シム(kinFactor)— なぜ卓上で「操縦感」が保てるか

卓上では US/OS・パワーオン挙動を、実効舵角の入力側シム `kinFactorEff = 1 + kinFade·(kinFactor − 1)`(と `steerKEff`)で再現しています。これにより**操縦感はクラシック版(キネマティック)譲り**のまま、限界挙動(飽和・滑り・90°超過渡)だけ動力学に委ねる、という二段構えになっています。較正は `test_dyn.mjs` の「calib fit」シナリオ群で行い、卓上はバイト単位で従来挙動を再現する契約(std/dyn の出力不変)を満たします。

フルスケールでは `kinFade=0` でこのシムを外し、等方実μ+空力+早期ピーク F4 曲線という「US/OS の物理母体」がそろうため、シムなしで本物どおりの挙動が出ます。

## 9. 現実と違う点・利用上の注意(まとめ)

- **速度表示は相対補正**。卓上の実速度は遅すぎて体感と合わないため、全開を サーキット≒350 / 峠≒180 km/h へ写像。**物理計算・判定・タイムには影響しない**(フルスケールのみ実速度を直接表示)。
- **操舵は左・中央・右の3値のみ**(実機 RumiCar と同じ)。連続可変ではない。サーボは有限速度 `steerRate` で実舵角へ追従。
- **左右輪の区別なし**(自転車モデル)。デフ・LSD・片輪空転などの左右差は表現しない。→ **精密 v2 エンジン(§13)はこの制約を撤廃**(4輪 two-track・デフ open/LSD・片輪空転あり)。
- **卓上の摩擦の異方性は便宜的**な工夫(§2)。実タイヤの物理ではない。→ v2 は等方の結合スリップ MF(§13)。
- タイヤ曲線は**簡易 Pacejka**。温度・摩耗・路面の細かな差は持たない(荷重感度はフルスケールのみ §4 の左右荷重移動として軸単位で導入)。→ v2 は路面属性 muDecay(§13)と**任意有効化のタイヤ熱・摩耗**(§13)を持つ。
- 車体: 0.19 × 0.08 m / ホイールベース 0.13 m / 最大舵角 ±24°(卓上)。最高速 0.7 m/s 基準に車種倍率。加速 2.5 / 制動 4.0 / 惰行 1.2 m/s² 基準。
- ToF 距離センサー: 左 +65° / 中央 / 右 −65° の3基(＋任意の後方1基)。各基は **25° の視野コーン(FoV)で扇内の最近反射面**を測る(実機 VL53L0X 準拠・§12)。範囲外/低信号は `RC_read` 系で −3、生読取は実機準拠の 8190。遠方は信頼できないため各サンプルは信頼区間 `CONF` で `>CONF`/−3 を「開放」とみなす(§12)。
- **学習プログラムの言語意味論**: 0 での除算(`1/0`・`x%0`)は**行番号付きの実行時エラー**(サイレントに Infinity を返さない)。Python は 負インデックス `a[-1]`(末尾)・連鎖比較 `a<b<c`(=`a<b and b<c`)・文字列反復 `"ab"*2`→`"abab"`・`%` フォーマット `"x=%d"%5`→`"x=5"` を実機同様に扱う。**ただし C の整数除算は非対応**＝本シムでは C の `/` も**真の除算**(`7/2`→3.5。実機 Arduino C は整数除算で `7/2`→3)。これは型追跡が必要(浮動小数リテラル `4.0` と整数 `4` を区別できない)ための意図的な制限で、割り算で整数が要る箇所は明示的に切り捨てる(`floor` 等)か、真値のまま扱うこと。

## 10. ToF の時間変化からの姿勢推定(レンジフロー)— なぜ本シムでは成立しないか

実機 RumiCar はジャイロ等の姿勢センサーを持たず、本シムも学習側に与えるのは**前方 ToF×3(左 +65° / 中央 / 右 −65°)＋任意の後方センサー(180°)＋任意の車輪エンコーダ(縦速度)**のみです(`api.js`)。ヨーレートや横滑り角 β を**直接読むセンサーは足しません**(実機準拠・方針 D-1)。

ではプログラム側で姿勢を**推定**できるか? が研究テーマです。原理は **レンジフロー**: 3本のレイの距離変化率 ḋ_i(=今回と前回の ToF 距離の差分)から、車体の (vx, vy, ω) を最小二乗で解き、横滑り角 **β = atan2(vy, vx)** を出す——というもの。±65° の広角ビームは横滑り vy を左右の差として強く拾うため、原理上は解けそうに見えます。これを試せるのが競技サンプル **「Range-Flow Estimator」(`comp_estimate`)** で、推定 β を Serial に出力し、画面 DEPTH パネルの**真 β**(物理が知っている正解)と突き合わせられます。

**結論: 本シムの条件では成立しません(NO-GO)。** 事前に定めた合格線「壁が視野に入る旋回で 推定 β の MAE ≤ 15° **かつ** 符号一致 ≥ 80%(本番実走)」に対し、実測は **MAE 10〜12°・符号一致 70〜72%**。しかも「β = 0(横滑りゼロ)と決め打ち」した自明推定(MAE 3°)に**負けます**=横滑りの**符号(右に滑っているか左に滑っているか)が当たらない**。根本原因は3つ:

- **壁法線の観測不能性(循環)**: 3本の広角ビームが別々の壁面に当たると、各ビームの局所的な壁の向きは1スキャンだけからは決まりません。正しい壁法線を知るには自己運動(vy を含む)が要り、その vy を出すには正しい壁法線が要る——**ニワトリと卵**。連立して解くと発散し、vy=0 と仮定して切り離すと壁が傾いて見えて推定が 0 に潰れます。
- **遠い壁の悪条件**: フルスケールは壁が数十 m 先。回頭による距離変化 ω·(腕の長さ) の係数が腕の長さ(数十)で、並進 vx/vy の係数(~1)を**圧倒**します。横滑りの寄与が回頭の寄与に埋もれます。
- **安定周回では真 β がそもそも微小**(平均数°)なので、「符号一致 ≥ 80%」は事実上「ほぼ完璧」を要求します。

この NO-GO は**隠さず**サンプルのヘッダにも明記しています。「素朴な壁法線仮定をどう改善するか」が、このサンプルを土台にした次の研究テーマです(I-1 と同じ"正直なガイド"方針)。

**追試(v3.54.0・Stage AO10): 地図事前分布つきでも不成立。** 「壁法線が観測不能なら、試走で覚えた**地図**を事前分布に使えば解けるのでは」という自然な再挑戦を、自己位置推定サンプル **「Self-Locator」(`comp_localize`)** で実測しました — 1次元ヒストグラムフィルタの自己位置(周回内 ~0.5 区画の精度)と地図の距離勾配を事前分布に、(左−右) ToF の変化率から β を逆算する構成です。結果は **MAE 10.3°・符号一致 14%** で、事前に固定した合格線(上記 J-1 と同一)に届かず **NO-GO**。つまり**姿勢(β)は、地図があっても ToF×3 からは読めない**、が本シムでの確定的な結論です。対照的に**位置**(コース上のどこにいるか)は同じ ToF＋エンコーダで周回内 ~0.5 区画まで推定できます(§13)。「**位置は解ける・姿勢は解けない**」— これが前方 ToF×3 という観測系の到達点であり、だからこそ v2 の戦略プログラム群は姿勢フィードバックに依存しない設計になっています(§13)。

## 11. ドリフトが成り立つ / 成り立たない条件

ドリフト(リアを大きく流して β を保ったまま走る)は、本シムでは**どこでも・どんなプログラムでも**出るわけではありません。**成り立つ条件と成り立たない条件があり、警告で先回りせず「走った結果」から自分で気づける**よう作ってあります(方針 J-2)。

**成り立つ最低条件:**
- **車種**: ドリフト車(`drift_fr` 等)。ノーマル車はフルスケールで等方摩擦+グリップ寄りに作ってあり(§2・§7)、持続スライド域がありません。
- **領域**: フルスケール。ドリフト車のフルスケールだけ縦摩擦 `muXDrift`(=0.48)を下げてパワーオーバー(駆動で後輪を空転)を復活させてあります。卓上/中スケールは byte 不変=この緩和を**かけません**。
- **走路**: 壁で囲まれたコース(競技サーキット)。壁が ToF の視野に入ることが、コーナーを認識して舵とスロットルを当てる前提です。
- これらが揃うと、サンプル **「Sustained Drift」(`comp_drift`)** や **「Slip Attack」(`comp_slip`)** で、コーナーごとにリアを流す挙動(旋回平均 \|β\| ≈ 50°・peak 180°)が観測できます。

**構造的に成り立たないこと(ToF だけでは不可):**
- **保持ドリフト(一定の β を保ち続ける)・全周ドリフト(コース一周ずっと流す)・逆ハン(カウンターステア)** は、前方 ToF だけの開ループでは**安定な解が存在しません**。リアが流れ始めると β は必ず 180°(フルスピン)まで回り切ります。約70通りの設定×6種の制御構造で全滅。理由は、ドリフト角の保持やスピンへの当て舵には**姿勢のフィードバック**が要るのに、その姿勢推定が §10 の通り成立しないから。だから `comp_slip` の「ドリフト」は、実体としては**直線=グリップ → コーナーで一瞬流して回り込む → 復帰、のリズム**で、保持でも逆ハンでもありません(ヘッダに明記)。

**成り立たない条件(同じプログラムを置く場所で変わる):**
- **開けすぎ**(壁が視野に無い広場=競技グラウンド): 壁距離でコーナーを判断する `comp_slip` がコーナーを認識できず、ドリフトが出ないまま**まっすぐ走って場外**。
- **狭すぎ・低速**(卓上の峠など): フルスケール用の絶対閾値が小スケールに合わず壁ガードに張り付いて**前進できない**。そもそも卓上は速度が低く走路が狭いため、滑りを"保持する空間"が無く grip ↔ spin に二極化します(I-1)。

→ 同じ `comp_slip` を、競技サーキット / 競技グラウンド / 卓上の峠 で走らせ比べると、**成立(リアが流れる)・開けすぎ(流れず場外)・狭すぎ(止まる)** の対比がそのまま体験できます。プログラム選択は領域やコースを強制しないので、**任意のコースに置いて走らせるだけ**で確かめられます。

### 精密 v2 エンジンでの再測定 — 「ドリフトはグリップに勝てるか」の go/no-go 表(Stage AO8)

なお上記の `muXDrift`(ドリフト車のフルスケールだけ縦摩擦を下げる緩和)は**動力学モデル(既定)の機構**です。精密 v2 エンジン(§13)はこのハックを**廃止**し(舵角も実機準拠の ±24° に統一)、ドリフトが出るかどうかを4輪の忠実な物理だけに委ねたうえで、「**ドリフト進入はグリップ走行より速いのか**」を専用ベンチコーナー(ヘアピン R5/6.5/8m・中速 R50・高速 R120 の各 乾燥/低μ 版)×車種×戦略の**決定論スクリプト実測**で表にしました — 結果は **全 20 セル NO-GO**(グリップの方が速いか、ドリフトが清潔に完了しない)。正本は `docs/stage_ao/drift_gonogo.md`。

機序は教材的で、(a) **回頭だけならドリフトが速い区間は実在します**(低μヘアピンで 90° 回頭 1.50s < グリップ 2.0〜2.35s)。しかし (b) **3値ステア(左・中央・右のみ)では平衡ドリフト角を連続保持できず**(当て舵の連続量調整ができない)、回頭後に β≈60° の滑走から**出口で再グリップできない**ため、「進入→回頭→再グリップ→立ち上がり」という一連の流れとして成立しません。つまり本シムの実機準拠の制約(3値ステア・姿勢センサーなし §10)の下では、**ドリフトはグリップに勝てない**が測定で確定した正直な結論です。それでも「制御された持続スライド」を学ぶ環境として、v2 では**卓上スリップタイヤ**(§13)を用意しています — 低速・低μで発進空転とパワーオーバーが安全に体験でき、任意有効化の**タイヤ摩耗**(§13)を足すと「ドリフトは後輪を消耗する=使いどころを選ぶ資源」まで含めて学べます。

## 12. ToF 距離センサーのモデル — 視野コーン・信頼区間・地面拘束・実車換算

前方3基＋任意の後方1基の距離センサー(ToF)は、v3.50.0(Stage AM・GitHub #27)から**「太さゼロの直線1本」ではなく、実機 VL53L0X の視野に合わせた 25° の視野コーン(扇)**として測距します。返すのは**扇の中の最も近い反射面までの距離**です。

### なぜコーンにしたか(#27「レーザーが壁の外に出る」)
中心1本の直線レイでは、壁沿い走行で道を横断する側の長いレイが**タイトなコーナーの線分端点のすぐ外**を掠め(`raySeg` の端点内判定 `u∈[0,1]` が全ミス)、描かれた壁を素通りして遠くの壁で止まります。これが「壁を突き抜けて見える」現象で、計算方式の退行ではなく初期からの潜在でした。実機の ToF は点ではなく **25°(半角12.5°)の広がりを持つコーン**で扇内の最近反射面を返すため、コーン化すると角の掠め抜けは**原理的に起きません**(扇内最近距離を返すので、中心1本より遠い値=壁の外へ伸びる値は出ない)。

- 実装: `geom.js coneNearest()` が各壁線分を扇の2境界(中心方位を ±12.5° 回転した半平面)へクリップし、残った部分線分上で原点への最近点を**解析的**に求める(半角<90°=扇は凸ゆえ交わりは1本の部分線分・**決定的/乱数なし**)。`sensors.js readSensor()` が全壁+他車エッジで最小を取る。返り形 `{mm, hit, origin, dir}`(`dir`=扇の中心方位・描画専用の後方互換な追加)。
- レンジは 0–2000mm(卓上)/領域スケール(フルスケール150m)。範囲外・扇内に反射面なし・低信号は **-3**。
- 表示(`hud.js drawSensors`)は 25° の扇を**距離2乗で淡くなる**グラデーションで塗り、**方向ごとに実際の壁/他車まで**伸ばして描く(v4.1.0・GitHub #30)。開いた方向はレンジまで伸び、壁のある方向は壁の上で終端する(空中終端なし・前方照射が他車を隠さず、壁抜けが見た目でも消える)。v4.0.1 までは扇全体を「扇内最近反射距離」の一定半径で打ち切っていたため、横の壁が扇の端(±12.5°)に掠っただけで前方が開けていても扇が短く見えた(#30)。**測距値は表示と独立に従来どおり「扇内最近反射面」**(ヒット点マーカ・数値ラベルがその位置と値)。
- 後方センサー(`readRear`)も**同一機構**(`readSensor(SENSOR_REAR)`)。

### 信頼区間(CONF)— 遠方は信頼しない
実機 VL53L0X は**地面反射**などで遠方の測距が信頼できません。地面拘束は `d = h / tan(12.5°) ≈ 4.51·h`(搭載高 h≈3.3cm(1/32)→ ~15cm・h≈4.4cm(1/24)→ ~20cm)。RumiCar 公式エクササイズ `Exercise-3.2` の判断閾値(100/150/**250mm**)からソフト実効はおよそ **250mm**。そこで各サンプルプログラムは**信頼区間 `CONF`** を持ち、`>CONF` または範囲外(-3)の測距を**「遠い/開放」**とみなします(その方向は空いていると判断)。これはライブラリ一律の固定値ではなく**プログラム側のパラメータ**で、車体・搭載高・コース/領域スケールで変わります。

### スケールと実車換算
- **卓上コースは実機 RumiCar 模型の約2.5倍スケール**(廊下幅 ~550mm)。実機の 250mm は卓上単位でおよそ **640mm**(=250×~2.56)に相当します。ゆえに卓上サンプルの既定は **`CONF=640`**。**実機へ移すときは自機の車体・搭載高に合わせて ~250mm へ下げ、あわせて速度も落とす**旨をサンプルのコメントに明記しています。
- **フルスケール競技サンプル**(`comp_circuit`/`comp_drift`/`comp_slip`/`comp_estimate`/`recon_racer`)は実車レーダ相当の設計(sensorMaxMm=150m)なので、信頼区間も**レーダ地平 150m(`CONF=150000`)**に据えます(実機 ToF の正直値 ~5m はコメントで明記)。
- **開ループ演目**(ショー/ゼロカウンター)や**車輪エンコーダで走るサンプル**(TC ローンチ/ABS)は測距航法をしないので信頼区間パラメータを設けません。

> 補足: この変更は測距・走行・決定論を**意図的に**実機へ寄せるものです。卓上の物理 byte とレース記録の verifyHash は新しい値へ**基準化し直し**、記録には engine 版(`engineFingerprint.appVersion`)が刻まれるので、旧記録は「当時の版で記録・現行版では完全再現しない可能性」の注記対象になります(改変せず条件付きで保持)。

## 13. 精密動力学エンジン v2 — 4輪 two-track・インパルス接触・タイヤセット・熱と摩耗(Stage AO)

v3.52.0 から、3つ目の物理エンジン**「精密 v2」**を選べます(ツールバー下「物理エンジン」セレクト。フルスケール領域では v2 を推奨として提示・**卓上の既定は従来どおり動力学モデル**=既定のままなら挙動・記録・決定論ハッシュは byte 単位で不変)。実装は `public/js/physics_v2.js`(車両)＋`public/js/contact_v2.js`(接触)。§1〜§8 のシングルトラックモデルとの違いを、実装に即して以下にまとめます。

### 13.1 4輪 two-track — 左右輪を持つ車体
- **輪別の垂直荷重 Fz**: 前後配分(§4 の縦荷重移動)に加えて**左右の荷重移動**(横加速度×重心高)を前後軸へ `rollBalance ζF` で配分し、ダウンフォース(§6)を足して**4輪それぞれの Fz** を持ちます(床は 0=浮き輪)。内輪が軽くなる・外輪に荷重が乗る、が輪単位で出ます。
- **結合スリップの Magic Formula(robust 形)**: 各輪のタイヤ力は、横スリップ角と縦スリップ率を合成した総スリップ σ に対し `g(σ)=sin(C·atan(Bp·σ))` で立ち上がり〜ピーク〜減衰を表します。係数は**ピーク後の漸近比 muDecay ただ1つから閉形式で導出**(`C=2−(2/π)·asin(muDecay)`・`Bp=tan(π/(2C))`。`g(1)=1`(ピーク)・`g(∞)=muDecay` を数値検証済)。動力学モデルの「縦横で別々の簡易 Pacejka＋摩擦円で束ねる」に対し、v2 は**結合則そのものがタイヤ曲線**です。
- **緩和長(relaxation length)**: タイヤ力は瞬時に立ち上がらず、走行距離に対する1次遅れで追従します(**陰的 Euler=無条件安定**)。切り返しの過渡・高速でのダンピングが自然になります。
- **アッカーマン操舵・β依存の横向き抗力・u² のみのダウンフォース**(横滑り中は失われる=ドリフトはダウンフォースも捨てる)も v2 で導入。

### 13.2 駆動系 — デフ・車輪 ODE・モーターブレーキ
- **定出力ドライブトレイン → 軸配分 → デフ**: オープンデフ(左右等トルク=内外輪速差は幾何どおり)と **LSD**(平滑な粘性結合・不連続な sign() を使わない)を持ち、パワーオンで挙動が変わります。
- **車輪の回転 ODE**: 各輪の回転速度を状態に持ち(剛性条件は自動サブステップ)、発進の**片輪空転**・制動ロックが輪単位で創発します。エンコーダ公開面 `RC_wheel_speed` は軸平均=**学習 API は無改変**です。
- **モーターブレーキは駆動軸のみ**(§4 と同じ実機準拠)。v2 では輪単位に効くため、FR の制動は「後軸ロック=サイドブレーキ相当」がより忠実に出ます。制動距離は軸配置依存(実測 AWD 33.7m・FF/FR はより長い)で、これは実機特性の忠実な帰結として明記します。
- **車輪 ODE の半陰的化(卓上/中スケール・v4.0.0)**: 車輪回転 ODE は剛性が高く、陽的 Euler では発散回避に多数のサブステップを要します(卓上 v2 で平均 ~253)。グリップ十分なタイヤの卓上/中スケール域では**車輪 ODE を半陰的(backward Euler)化**してサブステップ数を約1/9(平均 ~28)へ削減し、大幅に高速化しました。**フルスケールと低グリップ(slip)域は従来どおり陽的(適応サブステップ・§5)**で、既定の卓上物理・決定論ハッシュ f0〜f3・公式/正準記録は不変です。卓上 v2 を opt-in した走行だけは数値が変わり、以前の記録は「(当時 vX)」注記で正直に保持されます。

### 13.3 接触モデル — 「止めて取り消す」から「押し返す」へ
動力学モデルの衝突解決は「移動を取り消して停止」(原子的姿勢棄却)でした。v2 は**剛体力学のインパルス接触**です:
- **掃引 CCD**(高速でも壁を貫通しない=96m/s×薄壁で貫通ゼロを機械検証)・**壁2点マニフォールド**・**法線/接線インパルス**(壁は反発 0・接線はクーロン摩擦 μc=0.5×grip)・**split-impulse 位置補正**(貫入をエネルギーを足さずに解消)。
- **車車は運動量交換**: 側突(Tボーン)で角運動量が受け渡され、押し合い・弾き合いが物理として出ます(運動量保存 ≤1e-6 を機械検証)。
- 壁との強い衝突(法線接近速度 > 閾値)は従来どおり**レース規則のクラッシュ判定**へ、スタック(前進指令でも動けない)は**リカバリ操舵**へ接続されます。
- 全壁走査を避ける**ブロードフェーズ格子**(セル=2×車長)を導入し、候補限定と全壁走査の**結果一致を差分ゼロで機械検証**しています(速くするが答えは変えない)。

### 13.4 フルスケール較正 — 実車らしさの目標帯
最高速 300〜360 km/h(抗力律速)・横グリップ容量 低速 1.40g/高速(ダウンフォース込)≥1.8g・**v=√(μgR) のコーナー進入則**(1.0×維持/1.15×喪失)・FR パワーオン OS/FF US/リフトオフ OS の創発を、帯を実装前に固定して較正済みです。発進で駆動軸グリップを超えるとホイールスピン(パワーオーバー)が輪単位で出ます。

### 13.5 タイヤセット(normal/slip)と路面属性 muDecay — 卓上ドリフト学習環境
実機 RumiCar の「タイヤを滑りやすいものに交換して低速でドリフト練習する」を再現するため、v2 では車両ごとに**タイヤセット normal / slip** を装備できます(定数は領域別較正: 卓上 slip は μ0≈0.20=発進空転・パワーオーバーが卓上でも到達可能・フルスケール slip はハードコンパウンド相当 μ0≈0.9。normal のままなら卓上は「通常ドリフトは起きない」実機観察と一致)。またコース側に**路面 muDecay 属性**(ピーク後の滑りやすさ)を持たせられます(低μ路面)。§11 の go/no-go 表はこの仕組みで測りました。

### 13.6 タイヤ熱・摩耗(任意有効化)— タイヤを「戦略資源」に
「タイヤ摩耗」を ON にすると、各輪が**滑り仕事率 P=摩擦円利用率×正規化スリップ速**(無次元=卓上⇔実車で同じ尺度)から**温度**(1次緩和・冷間/最適/過熱)と**摩耗**(単調累積)を決定論的に積み上げ、限界グリップを `clamp(fT·fW, [0.9, 1])` で変調します — **合計効果は 10% 以内にクランプ**(摩耗が勝敗を支配しない設計)。実測では、同じ時間のドリフト周回(slip FR)の後輪摩耗はグリップ周回の**数万倍**で、「ドリフトは後輪を消耗する=使いどころを選ぶ資源」「常時ドリフト戦略は長丁場で自滅しうる」が測定として出ます。HUD に輪ごとの摩擦円利用率・温度・摩耗の 2×2 タイヤ図が出ます(**表示のみ**=物理は HUD を読み戻さない)。既定 OFF では挙動・ハッシュとも従来と完全一致。

### 13.7 決定論と互換性 — 既定では何も変わらない
エンジン(v2)・タイヤ(slip)・試走(recon)・摩耗(wear)は、**非既定を選んだときだけ**レース記録の正準表現(verifyHash の素)に刻まれます。つまり**既定のままの卓上物理・過去の決定論レース記録・公式記録はすべて byte 単位で不変**、非既定の記録は条件ごと刻まれて後から完全再現・検証できます(記録には engine 版も刻まれます)。

### 13.8 v2 で分かったこと — 正直な測定結果の総括
v2 は「速くて派手」を作るためでなく、**実機準拠の制約(前方 ToF×3・3値ステア・姿勢センサーなし)の下で何が成立し何が成立しないかを忠実に測る**ために作りました。結論はどれも隠さず教材にしています:
- **ドリフトはグリップに勝てない**(§11・全 20 セル NO-GO・`docs/stage_ao/drift_gonogo.md`)。回頭だけなら速い区間は実在するが、3値ステアでは出口再グリップが成立しない。
- **姿勢(β)は地図があっても読めない**(§10・レンジフロー NO-GO＋地図事前分布つき再挑戦も NO-GO)。
- **位置は解ける** — 自己位置推定サンプル「Self-Locator」(`comp_localize`)は、エンコーダのデッドレコニングを骨格に、毎周のループクロージャ(スタート壁パターンの照合)で再アンカーし、ToF 指紋のヒストグラム照合を弱い補正に使って**周回内 ~0.5 区画**の自己位置を出します(他車がいても残差ゲーティングで壁と他車を分離・前方検知 96%)。ただし**絶対位置はループクロージャの原点精度(~2.6 区画)が律速**で、対称コースでは ToF だけでは縮まりません。そして意外な正直値として、**この清潔なコースでは ToF 地図照合はエンコーダ単独に勝てません**(照合ノイズ>周回内ドリフト)— 照合の真価は補正でなく、信頼度・他車分離・復帰にあります。
- **精密な速度プロファイル計画の純利得は、均一・対称なコースでは概ね中立**。戦略レーサー「Apex Strategist」(`strategist`)は試走(下記)で覚えた地図から曲率→目標速度の前進/後退パス計画を持ちますが、実測の速さの大半は「試走が"踏める"と保証したことによる攻めチューン」から生まれ、コーナーごとの精密制動は (a) 全コーナー同 R のコースでは差が出ず (b) 自己位置の絶対精度(上記)が足りず安全に踏み込めない、の2つの理由で中立でした(Circuit Racer 比 11% 速いが、その機序は正直に「recon 由来」)。
- **事前試走(spec.recon)**: 🏁 レース/📋 開催で**試走 0〜3周**を選ぶと、各車が本番前に単独・計時外でコースを下見してから発走します(決定論・公式記録にも刻まれる)。自前で下見する自己完結型(Recon Racer)にはほぼ冗長で、**地図を前提に計画する戦略プログラムのための機構**です。

### 13.9 勾配(坂道)の物理 — 峠コースの下り(v4.0.0)
- **世界方向の重力射影**: 勾配は車体前方への一定加算ではなく、**世界座標の坂の向き**に対する重力成分 `gFwd = downhill·cos(θ−slopeDir)` として効きます(θ=車体方位・slopeDir=坂の下り方向)。向きに応じて**登坂で減速・下降で加速**が正しく出ます(以前は常に前方へ加算する「コンベア」で、登坂でも加速していました)。静止からの**転がり出し**、オプションで**勾配による静的な前後輪荷重移動**も持てます。
- **道追従の坂方向(峠コース)**: 峠は道が連続的に下るため、坂方向 `slopeDir` を**中心線の接線(進行方向)へ毎サブステップ更新**します(固定方向だと switchback で弧の一部が逆行してしまうため)。`downhill = g·sinθ` として elev バッジ含意の勾配と整合させ、峠の elev は現実的な勾配(上限 ~15%)へ正しました(elev は表示専用の装飾値でしたが、物理的に意味のある値へ整合)。下り較正後も最高速は駆動サーボの上限で頭打ちになるため、下りは主にコーナー立ち上がりの加速を強めます。
- **既定は不変**: downhill=0(非峠コース)は従来経路で byte 不変。変わるのは峠コース・勾配 v2 の走行のみで、当時の記録は「(当時 vX)」注記付きで正直に保持されます。
