RumiCar Simulator v8.2.0

🏁 最速プログラム ⧉ GitHub

使い方

1. コースを選ぶ

  • 画面右上の言語セレクタで日本語/Englishを切り替えられます (選択は保存されます)。操作系UIと実況メッセージが対象で、この長文ヘルプ本文の英訳は順次対応します。
  • コース関連の操作 (コース選択・コース編集) は一人称ビューの上にまとめてあります。「コース編集 ✎」で壁・スタート・フィニッシュを自作し保存できます (★付きで一覧に追加)。
  • 各コースには難易度★ (★1〜5)・推奨領域 (卓上/フルスケール)・🔰入門のバッジが付き、選ぶ前に向き不向きが分かります。起動時はまず入門コースから選ばれるので、いきなり完走しにくいコースに当たりません。フルスケール専用のコースを選ぶと走行領域が自動でフルスケールに切り替わります。
  • 峠コース (スイッチバック / 架空ロングワインディング) は周回ではなく頂上→麓のスタート/ゴール型。下りの重力で速度が乗るためブレーキングが鍵で、ゴール到達タイムを競います。高低差は一人称ビュー下の「立体プレビュー」で表示。高低差違いの複数モデルがあります。
  • ウェット路面コース (雨) はグリップが低く、攻めるとテールの出る車はスピンしやすく、アンダーの車は安定。条件で有利な車種が変わります。

2. 車両を用意する

  • 「＋ 車両追加」で最大6台まで並走できます。各列で車種 (ノーマル/ドリフト × FF/FR/4WD) を選択。
  • 車種を選ぶと、その車に最適化した最速プログラムが自動で読み込まれます (Fable Racing Line)。

3. 走行プログラムを選ぶ・作る

  • 走行 メニューから選べます:
    • 🏎 汎用・実機準拠 — Fable Racing Line — 車種別の基礎→応用プログラム6種。センサーで判断して走る=実機 RumiCar でそのまま動くのが基本です。
    • 🏁 sim最適化・競技 / 🎪 sim最適化・ショー — フルスケール領域や動力学モデルなどこのシミュレータ向けに最適化した演目(実機・他コースでの汎用性は下がります)。
    • 🌐 みんなの投稿 — 利用者が GitHub に投稿したプログラム。誰でも選んで使えます。
    • 汎用 (壁回避サンプル) — シンプルな基本プログラム。
  • 設計原則: 基本は「センサーで判断して走る」=実機でも他コースでも動く頑健なコードです。車両パラメータに合わせた作り込み(物理特性チューニング)はレース最適化という応用で、禁止はしませんが汎用性は下がります。まずはセンサー反応で書き、最適化は次の段階として捉えるのがおすすめです。
  • 他の車種用のプログラムを別の車に入れて比較もできます (例: 攻めの 4WD 用を FF 車に入れるとアンダーで膨らむ)。
  • エディタで直接編集でき、編集すると「(カスタム編集)」表示に変わります。📄 (既定サンプル)・GitHub URL 取込・「参照」(GitHub のプログラム閲覧)・⬆ (ファイル) からも読み込めます。言語は Arduino C++ / Python / JavaScript。

4. 走らせる

  • 自動 ▶ で全車同時スタート。一時停止 ⏸ 中は ステップ ⏭ で1周期ずつ実行でき、実行中の行がハイライトされます。
  • 停止中は 手動 ボタンまたはキーボードの矢印キーで選択車を運転できます (PWM スライダーで出力調整)。
  • 車体はマウスでドラッグして好きな位置に置き直せます。

5. 観察する

  • 各列に状態・周回数・測距 (左/中/右)・速度 (km/h)・シリアル出力をリアルタイム表示。
  • 表示オプション: センサーレイ / 距離ラベル / グリッド / 一人称ビュー。車体スケール・軌跡長・再生速度 (0.1〜3×) も調整可能。
  • フィニッシュライン通過でラップ計測。ベストラップはコースごとにブラウザへ保存されます。
  • 右上の「テーマ」で画面配色を5種から選べます (保存されます)。

6. GitHub で共有する (作る → 走らせる → 保存 → みんなで再利用)

  • コースを共有: コース編集で作ったコースを「🌐 GitHubで共有」ボタンで投稿します。JSON が手元に保存され、GitHub の投稿ページが開くので、そのファイルを置いてコミットしてください (プルリクエストになります)。承認されると全利用者の「🌐」コースに並びます。
  • プログラムを共有: 編集して納得したら各車の「🌐保存」ボタンで別名保存 (上書きしません)。ファイルが手元に保存され、GitHub の投稿ページが開くので、そのファイルを置いてコミットしてください。承認されると「🌐 みんなの投稿」に並び、誰でも再利用できます。
  • 投稿には GitHub アカウントが必要です (書込権限が無ければ自動 fork)。削除は GitHub 上で管理します。

7. プログラミング API (主要)

  • RC_steer(LEFT / CENTER / RIGHT) — 操舵 (3値・実機準拠)。比例操舵サーボ(任意装備)を選んだときだけ RC_steer(方向, 0〜255) で舵の強さも指定できる (未装備なら 0 を返して指令は変わらない)
  • RC_drive(FORWARD / REVERSE / FREE / BRAKE, pwm) — 駆動 (pwm 0〜255)
  • sensor0/1/2.readRangeSingleMillimeters() (C++) / get_distance() (Python) — 測距 [mm] (左/中央/右)
  • RC_read(LEFT/CENTER/RIGHT) — 測距の別形 (範囲外は -3)
  • 信頼区間 (CONF): 内蔵サンプルは「これより遠い測距や範囲外 (-3) は信頼せず開放とみなす」しきい値 CONF を持ちます。実機 ToF は遠方が地面反射などで信頼できないためで、卓上は実スケール換算で約640mm、実機へ移すときは自機の搭載高に合わせて約250mmへ下げます (詳細は 🔬 物理モデル)。
  • Serial.println(...) / print(...) — シリアル出力、delay(ms) / time.sleep(s) — 待機

8. もっと詳しく (GitHub)

  • ヘッダー右上の 「⧉ GitHub」 から RumiCar の GitHub (RumiCar-group/RumiCar) をワンクリックで開けます。各車カラムの 「参照」 でも GitHub のサンプル(プログラム/コース)を直接ブラウズして取り込めます。
  • 走行ロジックの解説: 車種別プログラム「Fable Racing Line」の設計思想・各車の物理特性に基づく定数の意味・実車でのチューニング手順は GitHub の programs/README.md にまとめてあります 〔RumiCar-group/RumiCar の programs フォルダ〕。
  • 各プログラム本体 (.ino) の冒頭にも「なぜこの設定にしたか」を物理特性とともに記載。実機 RumiCar でもそのまま動作します。
  • コースのカタログ・投稿方法は同リポジトリの courses/README.md を参照してください。

仕様と制限

車両・物理モデル

  • 物理エンジンは3種から選べます (ツールバー下「物理エンジン」セレクト)。既定は動力学モデル (タイヤが生む力を積分するシングルトラック=自転車モデル・簡易物理で実機の厳密な再現ではありません)。クラシックは従来のキネマティック物理、精密 v2は4輪 two-track＋インパルス接触の精密エンジン (フルスケール推奨)。卓上の既定は互換維持のため動力学モデルのままです。
  • 車体 0.19 × 0.08 m / ホイールベース 0.13 m / 最大舵角 ±24°。操舵は実機同様 左・中央・右の3値のみです。
  • 最高速 0.7 m/s (PWM 255 時) を基準に車種ごとの倍率がかかります。加速 2.5 m/s² / 制動 4.0 m/s² / 惰行減速 1.2 m/s² 基準。
  • 画面の速度表示は体感に合わせた「相対補正表示」です (卓上スケールの実寸 km/h は小さく感覚と合わないため、全開を サーキット≒350 / 峠≒180 km/h の目安へ写像)。物理計算・判定・タイムには影響しません。
  • 👉 運動方程式・摩擦円・タイヤ曲線・空力・領域スケールの数式つき解説はツールバーの 「🔬 物理モデル」 にまとめてあります。

車種特性 (6種)

  • ノーマル FF: アクセルONで強アンダー、発進空転大、制動安定。FR: よく曲がるがパワーオンで巻き込み・制動時リアが軽い。4WD: 発進最速・安定。
  • ドリフト FR/4WD: 旋回中に強くアクセル (目安 PWM 220 以上) を入れると、タイヤのグリップ円を超えて滑り出します (硬いしきい値ではなく速度・舵角で滑り出し点は動く連続判定。→「🔬 物理モデル」参照)。旋回中の急ブレーキでも滑ります。FRは大きく回頭、4WDは車体ごと流れて回復が速い。
  • ドリフト FF: 高速旋回中のアクセルOFF/減速でリアだけが流れ、再加速で収束します (パワーでは滑りません)。

センサー

  • ToF 距離センサー3基 (左 +65° / 中央 / 右 -65°)＋任意の後方1基。各基は 25° の視野コーン (FoV) で扇内の最近反射面を測ります (実機 VL53L0X 準拠)。計測レンジ 2,000 mm。
  • 範囲外は RC_read 系で -3、生読取 (readRangeSingleMillimeters 等) は実機準拠の 8190 を返します。
  • 「他車を障害物にする」ON のとき、他車の車体もセンサーに映り衝突対象になります。

実行モデル

  • ユーザープログラムの loop() は 20 Hz、物理演算は 60 Hz で実行されます。delay() は次の loop 呼び出しを遅らせます。
  • 壁に接触するとクラッシュ (恒久停止)。初期化 ↺ かドラッグで復帰できます。「衝突で自動復帰(切り返し)」をONにすると、恒久停止せず後退して開いた側へ切り返し、自動で走行を再開します。他車との接触はその場停止のみ (前が空けば再発進)。

プログラミング言語の対応範囲

  • Arduino C++ と Python は教育用サブセットのインタープリタです。変数・四則演算・if/else・for/while・関数定義・上記 API をサポートします。
  • 外部ライブラリの include/import、クラス定義、ポインタ、文字列の高度な操作などは使えません。JavaScript はブラウザネイティブ実行 (setup/loop 関数を定義)。
  • 無限ループ等の暴走は1反復あたりのステップ上限で打ち切られます。

その他

  • 最大6台同時走行。シリアル出力は約8,000字で古い分から破棄されます。
  • ベストラップ・自作コース・テーマ選択はこのブラウザの localStorage に保存されます (サーバーには送信されません)。
  • GitHub への共有 (コース/プログラム/車種) はプルリクエスト方式です。投稿内容は GitHub の公開リポジトリ (RumiCar-group/RumiCar) に保存され、承認後に全利用者へ反映されます。

システム仕様（技術アーキテクチャ）

このシミュレータは静的配信の単一ページアプリ (SPA) です。サーバーに状態を持たず、物理・学習プログラムの実行・描画はすべてブラウザ内で完結します。以下は外部からデータで拡張・自作するための技術仕様です (実装＝ソースを正とします)。コースデータの書式は別ダイアログ「📐 コースデータ仕様」にまとめています。

システム構成

  • 配信: public/ をそのまま配信 (Docker rumicar-simulator)。CSS/JS/HTML/courses.json は編集→ページ再読込で即反映 (再ビルド不要)。
  • 主要モジュール (ES Modules・public/js/): 物理エンジン＝physics.js (キネマティック) / physics_dyn.js (動力学・自転車モデル) / physics_v2.js＋contact_v2.js (精密 v2・4輪 two-track＋インパルス接触) / sensors.js (ToF) / runner.js (実行ループ) / fleet.js (最大6台)。学習側＝api.js (RC_*/rc_* ホスト) / programs.js・samples.js (内蔵プログラム) / interp/ (lexer・parser_c・parser_py・evaluator)。コース/描画＝data/courses.json / course.js・course_editor.js / geom.js・depth.js・elev3d.js・hud.js・lap.js。UI/設定＝index.html・css/style.css・main.js・loader.js・config.js (定数/車種/CHANGELOG/版)・i18n/ (メッセージカタログ)。
  • 実行モデル: ユーザープログラムの loop() は 20 Hz、物理積分は 60 Hz。delay() は次の loop() を遅らせ、無限ループは1反復あたりのステップ上限で打ち切られます。

独自車種 JSON

  • 車種は車種ダイアログで作れます。「独自車種を追加」に JSON を貼るか、「フォームで作る」エディタ (スライダー/数値・下の JSON と双方向同期) で追加します。必須: key (一意のID) と name (表示名)。
  • 任意フィールド (未指定はノーマルFRの既定値で補完): mass (車重kg) / accel・brake・maxSpeed (加速/制動/最高速の倍率) / spin (発進空転) / yawGain (旋回ヨー) / us・os (定常アンダー/オーバー) / powerUs・powerOs (アクセルONで増すアンダー/オーバー) / liftOffOs (アクセルOFFのタックイン) / brakeOs (制動時オーバー) / slide (横滑り量)。各パラメータの意味は車種ダイアログのパラメータ表に記載。
  • drift: null＝滑らない。ドリフト車は {trigger, grip, gain, minSp, slipYaw, slipSlide, attack, release, brakeDrift} で滑り出し点と挙動を定義します。
  • 独自車種は localStorage rumicar.customCars に保存 (このブラウザのみ・サーバー送信なし)。登録済みの独自車種は一覧から個別に 編集／複製／削除できます。例: {"key":"light_fr","name":"軽量FR","mass":980,"accel":1.1,"brake":1.1,"maxSpeed":1.04,"us":0.06,"os":0.08,"powerOs":0.30,"drift":null}
  • 組込6車種の上書き: 組込車種もパラメータ表の「編集」でローカルに上書きできます (実験用)。上書きは localStorage rumicar.carOverrides に差分パラメータのみ保存し、出荷時の既定 (卓上の物理 byte) は変えません。「既定に戻す」(個別)・「全上書き解除」で完全に元へ戻せます。
  • GitHub 共有: 作った車種は「🌐 GitHubで共有」で RumiCar-group/RumiCar の cars/community/ へ別名投稿 (プルリクエスト・上書きなし) できます。承認された投稿車種は起動時に GitHub から取り込まれ (localStorage には保存しない)、車種メニューに「🌐 名前」として並びます。

プログラム API（学習側）

  • 対応言語: Arduino C++ と Python は教育用サブセットのインタープリタ、JavaScript はブラウザネイティブ実行 (setup/loop を定義)。
  • Arduino 系 API: RC_setup() / RC_steer(dir)・RC_steer(dir, 0〜255) (第2引数は比例操舵サーボ(任意装備)を積んだときだけ有効・未装備は 0 を返す) / RC_drive(dir, pwm) / RC_read(dir) (前方ToF距離mm) / RC_wheel_speed(axle) (任意装備の車輪エンコーダ・未装備 −1) / Serial.print()・println() / delay(ms)。dir は LEFT/CENTER/RIGHT。
  • Raspberry Pi 系 API: rc_steer/rc_drive/rc_wheel_speed/rc_clear、read_one_sensor()、read_all_sensors()、センサーオブジェクト sensor0..sensor3 (各 .readRangeSingleMillimeters()/.get_distance()。sensor3＝後方・任意装備)、time.sleep(sec)。
  • 共通の数学関数: abs/min/max/sqrt/floor/ceil/round、研究用に atan2/atan/sin/cos/hypot/pi (純粋数学＝物理状態の肩代わりではない)。
  • 範囲外コード: RC_read 系は範囲外で −3、生読取 (readRangeSingleMillimeters 等) は実機準拠の 8190。計測は前方3基 (左 +65°/中央/右 −65°)・レンジ 2,000 mm。
  • プログラムは GitHub RumiCar-group/RumiCar の community へ別名で投稿 (プルリクエスト) して共有できます。

コースデータ仕様 (courses.json)

同梱コースは public/data/courses.json (配列) で定義します。

共通フィールド (全 kind 共通)

  • name (必須): コース名。
  • kind (必須): コースの生成方式。
  • desc (任意): コースの説明。
  • name_en/desc_en (任意): 英語表示名・説明。
  • diff/beginner (任意): 難易度・入門印。
  • noRace (任意): フルスケール設計コースの印。
  • grip (任意): 路面グリップ。
  • bank (任意): 横勾配 (カント)。
  • muDecay (任意, 数値 0〜1): 路面のピーク後の粘り。タイヤが滑り始めてピークを過ぎたあと、横力が最終的にピークの何割まで落ちるかです。0.75=舗装 (落ちる)／0.92=ダート風 (落ちにくい)。実装で [0.35, 0.95] にクランプされるので、1.0 を書いても「落ちない」路面にはなりません(それには surface を使います)。精密v2 エンジンのみが解釈します。
  • surface (任意, 文字列): 路面種別。"paved"(既定・省略時) / "loose"(砂利・ダート・雪)。loose はタイヤが表層へ潜って材料を押しのける掘り込みを加えるので、横力のピークが滑り角 8° から 23° へ移り、そこを超えても舗装のピークを下回りません。muDecay がピーク後の落ち方を「緩める」だけ(実装で 0.95 にクランプされるので 1.0 と書いても落ちない路面にはならない)なのに対し、surface:"loose" は落ちない曲線そのものを作ります。ただし「滑りやすさ」は作りません — 同じ grip に掘り込みを足すと路面は一様にグリップが上がります。ダートらしさを出すには grip を下げたうえで併用してください。bank と違い kind を選びません。精密v2 エンジンのみが解釈します(掘り込みを「輪ごとの μ·Fz に対する比」として v2 の結合スリップ上で定義しているため、輪ごとの μ·Fz を持たない単軌道近似の「動力学」と、横自由度を持たない「クラシック」には足す先がありません)。未指定なら従来と完全に同じです。

🔬 物理モデル — いま車に何が起きているか

画面の中の車は、タイヤが路面に生む力を毎フレーム積分して動いています。アンダーステアもドリフトもスピンも、個別の演出ではなくこの力学から自然に出てくる結果です。以下は「なぜそう動くのか」を数式とともに辿れるように書いてあります。各見出しは後から読み返し・自分で調べた内容との対比に使ってください。

1. 解いている運動方程式 — シングルトラック(自転車)モデル

  • 前輪・後輪を左右まとめて1本ずつに集約した「自転車モデル」です。重心 (CG) を基準に、3つの状態量を時間積分します。
    u = 車体の前後速度  |  vlat = 車体の横速度  |  r = ヨーレート(回頭の角速度)
  • 運動方程式(質量 m・ヨー慣性 Iz・前軸距離 a・後軸距離 b):
    m·(u̇ − vlat·r) = Fx,前 + Fx,後   (前後方向)
    m·(v̇lat + u·r) = Fy,前 + Fy,後   (横方向)
    Iz·ṙ = a·Fy,前 − b·Fy,後   (回頭モーメント)
    回頭は「前輪が生む横力で頭を入れる」対「後輪が生む横力で頭を戻す」の綱引き。この差が残ると車は回り続けます(=ドリフトの自走)。
  • 3つの物理エンジンを切替できます(ツールバー下の「物理エンジン」セレクト):
    • 動力学モデル(既定): 上式の通り力を積分。速度の向きが車体の向きから大きくずれられる=横向き90°超のドリフトやバックエントリーが可能。
    • クラシック物理: キネマティックモデル。速度の向きが車体の向き ±45° に拘束されるため横滑りが構造的に出ません。動きは滑らかで初学者向け。
    • 精密 v2: 4輪 two-track＋インパルス接触の精密エンジン。フルスケール競技で推奨・卓上ではスリップタイヤのドリフト学習環境。詳細は docs/physics_model.md §13。

2. タイヤが出せる力には上限がある — 摩擦円

  • 各タイヤが出せる「前後の力(駆動/制動)」と「横の力(曲げる力)」は、合計が円(楕円)の内側に制限されます。これが摩擦円です。
    (Fx / (μx·n))² + (Fy / (μy·n))² ≤ 1   (n = そのタイヤの荷重, μ = 摩擦係数)
  • 「曲げながら全開」はできないのはこのため。前後に使い切ると横が残らず膨らみ(アンダー)、横で使い切ったところへ駆動を足すと滑り出します(オーバー/スピン)。
  • 現実との違い・モデル上の工夫: 卓上スケール(13cm・0.7m/s)では実際の μ≈1 だと横加速度が小さすぎて絶対に滑りません。そこで卓上では円をわざと縦長の楕円にしています(横 μy=0.19 ≪ 縦 μx=0.75)。「滑り出しが目で見える」ようにするための意図的な異方性で、実車のタイヤとは異なります。フルスケール領域では本物どおり等方の真円(μy=μx=1.4)になります。

3. 横の力はどこから出るか — スリップ角とタイヤ曲線

  • タイヤは「向いている方向」と「実際に進む方向」がズレると、その差(スリップ角 α)に応じて横力を生みます。
    小さいズレ: Fy ≈ C·α   (C = コーナリング剛性。タイヤの“踏ん張り”の強さ)
  • ズレが大きくなると横力は無限には増えず、あるピーク(αpeak)で頭打ちし、超えると緩やかに減衰します(簡易 Pacejka 曲線)。
    |α| > αpeak で Fy = Fy,max / (1 + kdecay·(|α| − αpeak))
    卓上は αpeak≈1.35rad と粘り、フルスケールは実タイヤ同様 αpeak≈0.25rad(≈14°)で早めにピークし限界後はやや深く落ちます。
  • アンダー/オーバーの正体: 前後の踏ん張り(コーナリング剛性)の比で決まります。前が先に限界=アンダーステア、後が先に限界=オーバーステア。車種ごとの us / os や前後剛性比がこれを決めています。

4. 前後の力 — 駆動・制動・荷重移動

  • 駆動力と制動力は駆動輪へ配分されます(FF=前のみ / FR=後のみ / 4WD=前後)。
  • RumiCar 実機の特性そのまま: ブレーキは摩擦ブレーキではなくモーターブレーキなので、駆動輪にしか効きません。だから FR は制動でリアがロック気味になり回頭(ブレーキドリフト)、FF は前だけ効いて直進安定、という挙動が構造から出ます。実測(フルスケール・40m/s から)では停止距離が FR 138.97m / FF 88.11m / AWD 65.85m と駆動方式だけで 2 倍以上違います。任意装備の〈4輪摩擦ブレーキ〉を選ぶと、同じ総制動力を前後配分で 4 輪へ配れます(既定はモーターブレーキのまま)。
  • 荷重移動: 加速すると荷重は後ろへ、制動すると前へ移ります。
    Δn = m·ax·(h/L)   (h=重心高, L=ホイールベース。本モデルは h/L=0.35)
    荷重 n が動くと摩擦円の半径 μ·n も前後で変わる → 「制動中はリアが軽い=滑りやすい」が出ます。

5. 車輪のスリップ率(フルスケール領域)

  • フルスケールでは車輪の回転そのものを状態にします。車輪表面の速度 vw=ω·R と路面速度 u の差からスリップ率 sを出し、縦力を縦版 Pacejka で決めます。
    s = (vw − u) / |u|  ,  Fx = μx·n·sin(C·atan(B·s)) / gnorm   (gnorm はピーク speak で 1 になる正規化)
  • これで発進の空転(ホイールスピン)と急制動のロックが創発します。どちらも縦に使い切るので摩擦円から横力が消え、グリップを失います。「車輪エンコーダ(任意)」を使えば前後の車輪速度差から s を読み、トラクション制御や ABS を自作できます。

6. 空力 — 抗力とダウンフォース(フルスケール領域)

  • 速度の2乗に比例する2つの空気の力が効きます。
    抗力 Fd = ½·ρ·Cd·A·u²   (常に減速側)
    ダウンフォース Fl = ½·ρ·Cl·A·u²   (荷重 n を増やす)
  • 「速いほど曲がれる」: ダウンフォースが荷重 n を増やし、摩擦円の半径 μ·n が速度とともに大きくなるためです(卓上には無い感覚)。
  • 最高速は自然に決まる: 駆動力 = 抗力 で釣り合った速度が頭打ちになります(設定値ではなく結果。約347km/h)。

7. 領域(スケール) — 同じエンジンで卓上から実車まで

  • 同じ動力学エンジンを卓上 / 中スケール(屋外RC) / フルスケール(実車350km/h)の3スケールで動かせます(ツールバー下の「領域」)。挙動の鍵は次の支配比:
    Ay* = (v² / R) / (μ·g)   (必要な横加速度 ÷ 路面が出せる横加速度。1 を超えると滑る)
  • 卓上 ↔ 中スケールは動的相似で繋がっています。長さを kL 倍するとき速度を Froude 相似 kV=√(kL·kG·kμ) 倍すると Ay* が不変 → 同じプログラムが、大きく速い世界でも同じ操作で同じように滑り出します。
  • フルスケールは相似を意図的に破った領域です。卓上の異方性ハック(μy≪μx)をやめて等方の実 μにし、空力を効かせます。だから卓上では届かない Ay*→1 が「速度を上げるだけ」で本物どおり起き、ドリフト車も“攻めて限界を超える”必要が出ます。

9. 現実と違う点・利用上の注意(まとめ)

  • 速度表示は相対補正。卓上の実速度は遅すぎて体感と合わないため、全開を サーキット≒350 / 峠≒180 km/h へ写像しています。物理計算・判定・タイムには一切影響しません(フルスケールのみ実速度を直接表示)。
  • 操舵は左・中央・右の3値のみ(実機 RumiCar と同じ)。連続可変ではありません。
  • 左右輪の区別なし(自転車モデル)。デフ・LSD・片輪の空転といった左右差は表現しません。
  • 卓上の摩擦の異方性は便宜的な工夫(上記2)。実タイヤの物理ではありません。
  • タイヤ曲線は簡易 Pacejka。温度・摩耗・荷重感度・路面の細かな差は持ちません。
  • ユーザープログラムの loop() は 20Hz、物理積分は 60Hz。ToF センサーは ±65°・3基、計測レンジは卓上2,000mm / フルスケール150m。
  • ToF は 25° の視野コーンで扇内の最近反射面を測ります (実機 VL53L0X 準拠・v3.50.0)。中心1本の直線ではないので、コーナーの角を掠めて壁の外へ抜けません (#27 の根治)。各サンプルは信頼区間 (CONF) を持ち、これを超える/範囲外の測距を「遠い/開放」とみなします (卓上は実スケール換算で約640mm、実機移行時は搭載高に合わせ約250mmへ下げ速度も落とす)。詳細は docs/physics_model.md §12。
  • 光の当たり方は既定では理想化しています。実機の有効測距は「標的から返る信号の強さ」で決まり、信号は 反射率 × cos(入射角) ÷ 距離² に比例します (上流ライブラリの setSignalRateLimit が実際にこのしきい値)。既定はこれを無視して「扇内の最近反射面」を必ず返しますが、ツールバーの ToF 光学モデル(実機相当) を ON にすると実機と同じ判定になり、①斜めから見た壁・暗い他車・扇を埋めない小さな標的は早く測れなくなり (-3) ②扇内に複数の面があると信号加重で混ざり ③カバーガラスのクロストークで遠方が少し短めに出ます。決定論(乱数なし)なので「センサーノイズ」とは独立に試せます。公式レースは強制 OFF。詳細は docs/physics_model.md §12。

11. 設計のQ&A — 開発中に実際に検証した「なぜ」

  • Q. ドリフト走行はグリップ走行より速くなりませんか? A. ほとんどの条件では、グリップ走行の方が速く走り抜けます。ヘアピン〜高速コーナー・乾燥/低μ・複数車種の組合せ(20セル)も、平地/下り5°/下り10°の3水準×24=72セルも、すべて NO-GO でした。回頭自体はドリフトの方が速い場面もありますが、横滑り角βがおよそ36°を超えると舵を中立に戻しても0.6秒では回復できないため、コーナー出口で再グリップして加速に転じられません。原因は舵の細かさではなく(任意装備の〈連続舵〉に替えてもGOは1つも復活しません)、車体側の回復限界です。ただし「どこでも勝てない」という意味ではありません。①壁で囲まれたタイトなヘアピンでは、グリップの幾何最善線がそもそも収まりません(10セル中8セル)。そこへ浅い滑り(旋回中の|β|ピーク12〜15°)を伴う能動的な運転を当てると、8セル中5セルは180°回りきって壁にも触れませんでした(後輪駆動のみ。4WDは同じ掃引で0/8)。壁とのすき間は0.03〜0.71m残ります。この5セルは逆ハンを一度も当てていません(到達舵角の最小が0%)。グリップ側を実際に走らせても通れません — 意図的な滑りを作らないグリップ走行では、この8セル(×2駆動=16行)で完走は0行(最長でも121°/180°)。同じドライバは対照セルでは2/2で完走します。ただし探索したのは定常円弧の2種類で、切り返し(多点旋回)の線はまだ測っていません(なお制動で実効半径を詰める線は原理的に届きません — 最小旋回半径は「ホイールベース÷tan(最大舵角)」で決まる速度に依存しない下限で、減速してもこれより内側は回れないためです。制動で回頭させることはタイヤを滑らせることであり、下の③の話に含まれます)。②自由空間には窓が1つだけ開きます — 壁のない廊下36セルのうち、いちばんタイトなR5×低μ×180°×後輪駆動の1セルだけは、ドリフト(|β|ピーク27°)がグリップより11.9%速く、進入速度が±10%ずれても崩れません。残る35セルは開かず、単発で速い5セルのうち頑健なのはこの1セルだけ＝多くの場合落ちているのは速さではなく頑健性です。③速いのは深いドリフトではなく浅い滑りです。アクセルで後輪スリップ率を制御する「ドリフト⇄グリップ切替」の運転を最適化すると、基準条件の8セル中7セルでグリップより速くなります(最大20.6%速い)が、その最適解の|β|ピークはすべて14.8°以下。「深く滑ること」(|β|ピーク20°以上)を制約にして同じ予算で探し直すと、解が見つかった16行すべてで浅い最適解より速くなりません(1.00〜1.28倍)。駆動力を2倍にしても最速解は浅いままです(ただし16行中5行では深い解もグリップは上回りました＝「深いと勝てない」ではなく「深くても最速にはならない」)。④2台走行でわざと横を向いて塞ぐ戦術は、自分が損をします — 先頭の平均ラップが15.78→23.19秒(+47%)に悪化し、通常走行なら582m前で終わるところ、後続に69m先行されます。なおどの表も有限の掃引格子の中での最善＝「その格子では見つからなかった」という意味です。実車のプロドライバーが行う限界域ドリフトとは条件が異なります。

  • Q. コースの「路面種別 (ルーズ)」は何をしますか? A. 砂利・ダート・雪では、タイヤが表層へ潜って進む先に材料の土手を作り、押しのけます(掘り込み)。この力は摩擦ではなく「押しのけた材料の量」で決まるので、滑らせるほど積み上がります。舗装の最適スリップ角が 5〜10° なのにダートで 20〜30° になるのはこのためです。コース定義に surface:"loose" と書くと、輪ごとの力の大きさに σ 比例・上限付きの項が足されます(F = μ·Fz·[g(σ) + dig·min(σ/digSat, 1)]・実効摩擦円 μ_eff = μ·(1+dig))。向きは変えず大きさだけを足すので、定常タイヤ力が常に散逸的であることも摩擦円 |F| ≤ μ_eff·Fz も壊れません。実測ではピークが σ=1 (滑り角 8.0°) から σ=3 (22.8°) へ移り、σ=2〜4 の横力/ピーク比は舗装の 0.94/0.89/0.86 に対し 1.14/1.19/1.16 になります。ドリフトへの効き方は素直ではありません: 低μベンチをルーズ化すると破綻せず回れるドリフト解は 38→202 run(×5.3)に増え、舗装では回れなかったヘアピンが 1 つ回れるようになりましたが、着手時の 2 つの見込みはどちらも確かめられませんでした — 「所要時間比が下がる」は掃引格子を変えると符号が反転し、「深い滑りで回れる解が増える」は合計の符号が掃引に依存します(既定 6 セルで 28→18・18 セルの系統掃引で 58→234)。セルごとに増減があり機序は特定できていません(最小回転半径は判別境界になっていません)。「滑りやすさ」も作りません — 同じ grip に掘り込みを足せば路面は一様にグリップが上がります。HUD とレースレポートの「摩擦円使用率」は正規化スリップを百分率にしたもので、v7.6.0/v7.7.0 ではルーズ路面のピークが 300% と出ていましたが、v7.8.0 から掘り込み路面ではその路面のピーク σ で正規化し、舗装でもルーズでも 100%＝ピークと読めます(表示層だけの話で物理は不変)。解釈するのは「精密v2」だけです — 掘り込みを「輪ごとの μ·Fz に対する比」として v2 の結合スリップ上で定義しているため、輪ごとの μ·Fz を持たない「動力学」(簡易 Pacejka と摩擦楕円は持っています)と、横自由度を持たない「クラシック」には足す先がありません。既定 (未指定/paved) では 1 バイトも変わりません。
  • Q. 「サス自由度(任意装備)」を選ぶと何が変わりますか? A. コーナーで荷重が移る「途中」の動きが変わります。既定(準静的)では、荷重移動は加速度に一次遅れで追いつくだけで行き過ぎることができません。装備を選ぶとロールとピッチがばねと減衰を持つ本物の1自由度系になり、切り返しで荷重が行き過ぎてから揺り返します。行き過ぎの大きさは減衰比だけで決まり(閉形式 exp(−πζ/√(1−ζ²))＝ソフト 37.2%・標準 4.6%・ハード 0%)、行き過ぎたぶんは荷重感度を通じて横グリップを過渡的に削るので、切り返しの瞬間だけ曲がりにくくなります(過渡アンダー)。定常のコーナリングは既定と厳密に同じです(相対差 1e-15)＝変わるのは過渡だけ。精密 v2 エンジン専用で、既定のままなら 1 バイトも変わりません。
  • Q. 「操舵サーボ(任意装備)」で〈連続舵〉を選ぶと何が変わりますか? A. 舵をどれだけ正確に置けるかが変わります。実機 RumiCar の操舵は左/中立/右の3値だけで、これは学習APIの基本仕様です。ただし3値でも中間の舵角は作れます——サーボは目標角へ一定の速さで動くだけなので、小刻みにオン/オフすれば平均化されて中間角になります(デューティ操舵)。ですから連続舵が変えるのは分解能であって帯域ではありません。3値では指令のたびにフル舵へ向かって流れるので、保持誤差が「1指令のあいだにサーボが動ける角度」に張り付きます(学習プログラムの実レート20Hzで平均 1.59°)。連続舵は目標角を直接置けるので、残るのは 0〜255 の刻みぶん 0.0235° だけ(指令レートにも領域にも依存しません)＝約68倍の改善です。ただし速くはなりません。 ドリフトの go/no-go 20セルを連続舵で取り直してもGOは1つも復活せず、サーボの速さを64倍にしても変わりませんでした。本当の壁は舵ではなく車体の回復限界で、横滑り角がおよそ36°を超えると舵を戻しても0.6秒では戻れません。連続舵は「速く走るための装備」ではなく「舵を正確に置くための装備」です。3エンジン全てで効き、既定の3値なら1バイトも変わりません。
  • Q. 「制動装置(任意装備)」で〈4輪摩擦ブレーキ〉を選ぶと何が変わりますか? A. 制動力の「配り先」が変わります(総量は変わりません)。実機 RumiCar のブレーキは駆動モーターの逆トルクだけなので、FR は後輪だけがロックし前輪は自由に転がったままです。実測(フルスケール・grip 1.0・40m/s→2m/s)で停止距離は FR 138.97m(0.588g) / FF 88.11m(0.926g) / AWD 65.85m(1.239g) と、同じ車重・同じタイヤなのに駆動方式だけで 2 倍以上違います。4輪摩擦ブレーキを積むと同じ総制動力を前後配分(既定は前60/後40)で 4 輪へ配るので、FR は 138.97m→63.40m と 54% 短縮します。AWD はほとんど変わりません(0.2%) — モーターブレーキでも既に 4 輪へ配られているからで、この装備が効くのは「制動が掛からない輪がある」車です。ロックは車輪の回転を解く方程式から創発します(コードにロック閾値はありません)。実測で配分を前45%→60%→75% と上げると前輪ロック率が 0.52→0.76→0.84 と単調に増え、後輪ロック率は 0.68→0.36→0.00 と単調に減ります。直線では 3 種の配分にほとんど差が出ません — 制動指令(4.013g)がタイヤ容量(1.40g)の 2.87 倍あり、どう配っても全輪が飽和するためです。配分が効くのは旋回中です。コーナー内で踏む「トレイルブレーキ」を、半径・進入速度・制動時間・路面μ・舵の型を振った2つの独立な格子(54セルと288セル)で測りました。言えること①: FR の後軸ロックは必ず減ります(平均 0.800→0.210 と 0.662→0.123・342セル中 増えたセルは0)。②: FR の旋回復帰は1セルも悪化しません(戻れたセルが 13→39 と 88→200・得138/失0)。③: FF は逆に後軸ロックが増えます(0.000→0.320)— モーターブレーキの FF は後輪に制動が一切掛からないので、4輪化すれば必ず増えます。常に安全になる装備ではありません。言えないこと: 横滑り角のピークが下がること — 平均は下がります(FR 55.1°→22.7°)が、セル単位では増える所があり(格子1で9/54・格子2で54/288)、これは法則ではなく連続量の記録です。⚠ 卓上・中スケールではこの装備は制動をわずかに弱めます(フルスケールとは向きが逆です)。同じ FR 車でフルスケールでは 2.11 倍強くなるのに、卓上・中スケールでは 1 倍未満になります。この向き自体は数値誤差ではありません — 同じ製品コードの陽的経路(参照解)でも 0.94 倍で、装備の性質です。v7.8.0 までは、その悪化が実際よりずっと大きく出ていました(卓上 0.76 倍・中スケール 0.77 倍＝停止距離が 3 割ほど伸びる)。原因は領域そのものではなく、卓上/中スケールで有効な車輪 ODE の半陰的化(高速化のための近似)が陰的更新の間に接地速度を凍結し、車体の減速に車輪が追随できず指令より小さい力しか路面へ届いていなかったことです(当時の実力/指令は既定のモーターブレーキで 0.59・4 輪へ配ると 0.43)。v8.0.0 で車輪の運動方程式を車体加速度と同一 substep で連成して是正し、現在は卓上 0.96 倍・中スケール 0.95 倍(参照解 0.94)＝悪化は 5% 以内(実終速で計算した減速度の比。停止距離では 3.5〜6.2% 長い)に収まります。半陰的化を通らない条件(低グリップ・スリップタイヤ・フルスケール)は従来どおり 0.96〜2.11 倍です。FF と 4WD は旋回復帰を失うセルがあります — 288 セルで FF は 18 セル失い 5 セル得(283→270)、4WD は 15 セル失い 8 セル得(258→251)。1 セルも悪化しないのは FR だけで、この装備は駆動方式によって損得が逆転します。精密v2 エンジンでのみ効きます(理由は物理解説 §13.16)。既定の〈モーター〉なら従来と 1 バイトも変わりません。
  • Q. 自分のブラウザで走らせたタイムと、GitHub上の公式レース記録が微妙に違うのはなぜですか? A. 浮動小数点演算(Math.sin等)はブラウザ・Node.js・OSの組合せでビット単位の極小差が出ることがあり、僅差の勝負ではその差が結果に響く場合があります。そのため公式記録は特定のNode.js環境で固定実行する「正準エンジン」の結果だけを採用しています。ご自分のブラウザでの結果はあくまで手元の参考タイムとしてご覧ください。
